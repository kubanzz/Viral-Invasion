# v075 内存与对象生命周期预检

本次只读现有报告、当前源码和已有测试，未启动浏览器、运行模拟／构建／测试，也未修改生产、测试或旧归档。仅写本文件及同名 JSON；原始报告指纹、精确数值与源码入口见 JSON。

原文 `AC-M16-04` 要求在实际目标设备进行 **10 分钟压力运行**，平均 FPS≥50、帧时间 p95≤33ms，无持续内存增长及致命控制台错误。这是可以用有限运行证据支持的目标，无须把它扩大成无限时间或全部设备均不泄漏。当前 v075 还需要同版本的 600 秒结果；v074 的十分钟基线有价值，但不能替新标签系统完成验收。

`usedSize` 是采样时占用的 V8 堆，包含尚未回收的垃圾；`totalSize` 是 V8 已分配容量，不能把容量增幅直接称为活对象泄漏。embedder、backing 分别记录，也不是总进程 RSS／原生 Canvas／GPU。natural 过程没有显式 GC；下降只是采样事实，不能冒充已观测到某次 GC 事件。

v075 的准备、warmup、正式测量合计到 elapsed 276.05，不是正式压力持续 276 秒，更不是十分钟。`acceptanceTenMinuteRun=false`、`postMemory=false`。其 30 秒 used 中位数为 13.39、23.62、22.91、21.16 MB，末尾又降到 6.66 MB；它反映大量临时分配与回收，但首末一分钟中位数上升 31.56%、监听器中位 34.5→48 仍应原样报告。单个低终点不能抹掉窗口上升，120 秒也不能给出 600 秒结论。

v074 的十个完整分钟 used 中位数非单调，期间 62 次下降；首末容量增加约 69.86%，而终后暂停三次 GC 后 used 为 5,710,424 B、capacity 为 6,430,720 B。回菜单后 used 为 4,675,096 B，重开 5／10 次为 4,780,472／4,844,016 B：十次 +168,920 B（3.61%），监听器始终 37，菜单节点 424→453→424。这支持**该机器、该 v074 驻心脏场景的有限十分钟内未观察到失控 V8／DOM 持续保留**，同时保留实际正增量。它不等于零字节增长，也不等于当前 v075 或真实结算循环的内存结果。

## 当前源码可界定的生命周期

- **标签缓存有硬界。** `SceneLabels` 测量 Map≤256，位置 Map≤128；逐帧清理当前 labels，替换 blocked／result；run:organ 或视口变化清位置缓存。anchor 只是 Vec 拷贝，不保存 GameState。测量缓存跨局保留但数量有界。
- **HUD 没有全局强引用旧树列表。** 淡化时间、槽位子元素、反馈文本和引导节点使用容器 WeakMap；槽位签名变化会替换旧值。当前容器及当前子节点有意保留；DOM 样式 Map／panels 数组是函数局部，Renderer 只保存当前数字矩形。
- **存在具体 DOM 分配抖动。** 约 20 Hz 的 textContent 更新，trait-strip 的 innerHTML 重建，以及有限预警期的 card 重建都会产生待回收对象。overlay 只有状态 key 变化才换整树，且使用一个 app 委托点击监听器。暂时较高 CDP node／listener 数不直接证明它们被永久保留。
- **渲染底图有意跨局保留。** 当前两个器官固定 2400×1500，landscapes 按 organ:width:height 缓存，正式模式至多两个键，不按 seed 新增。每个 2600×1850 底图若按四字节像素表面计为 19,240,000 B；这只是容量推算，不是已观测 RSS／GPU，也不能从约 0.4 MB backingStorage 读数声称它们不存在。标记轨迹按局／器官清理，每条最多四点。
- **监听器在页面初始化注册。** 单个 Controller 构造注册九个事件，另有一个 app 点击、一个 resize、一个 session bus 回调；start／menu 不再构造这些对象。一个生产 RAF 链持续运行。start／menu 换 GameState 与成长／战役控制器，清 campaignTransactions／deferred 和母核；未发现每次重开新增监听器的生产路径。音频只有一个 context，有限 cue 分组；oscillator 结束时清回调并断开节点。
- **大多数战斗历史也有界。** events≤512，战斗／战役／成长历史≤128，chainRoots≤256，acceptedHistory 每 tick 清理，runMetrics 临时帧≤256、累计部分是固定字段计数，行为分箱为 90 秒窗；效果、尸体、细胞按既有生命周期清理。数字累计本身不等于每次保留一个对象。

## 两类真实账本保留

**`campaignTransactions` 确实按局内操作增长。** 它是 host 接受命令的幂等 Set，防止重复施加伤害、感染、路由等副作用，只在 start／menu 清空。已经激活且离场的器官有开放源时，累计 10 秒宽限后每 **5 秒**产生独立 background load ID；即使每次离场的 15 点伤害预算用完，感染 load 仍继续，因此不是永远固定大小。`campaign.transactionIds` 另保存已接受 travel 与一次危机源事务。反复旅行也会增加 ID。暂停或结果页仍保留同一局；10–15 分钟只是目标时长，没有强制局寿命上限。

这不是 GC 抖动，也不是标签／DOM 泄漏，而是有真实语义的局内记账。600 秒有限窗口内，两个器官各按 5 秒调度的保守估计最多约 242 批背景操作、每批至多两个 host ID，即 484 个背景 ID；3 秒旅行冷却下最多约 201 次新旅行，外加有限启动事务。此估计是新测量窗口增量上界，不包括准备阶段，也不是无限长局的常数界。实际上同一时刻只有一个器官离场，通常远低于此保守界。

现有两次驻心脏压力都没有激活肺，故没有触发这个后台分支。现有 `campaign.test.ts:137` 验证长间隔单批、宽限、关闭通路及损伤预算，`:155` 验证三秒反复旅行不重置离场宽限；它们不是 host 私有 Set 大小测试。

若以后要硬限制账本，合理方案是把有限的一次性 spawn／route／crisis 键与周期操作分开，对每个 organ×operation 的后台命令保存已接受 tick／sequence 水位，对 travel 另保存已接受水位。这样旧命令仍会被拒绝，又不必保存每个五秒 ID。必须先定义重复、过期、同 tick 嵌套、deferred 和未接受命令的顺序语义。**不能简单丢掉最旧 N 个 ID 或按墙钟过期**，否则旧副作用可能重放，暂停语义也会改变。当前有限十分钟结论可如实限定场景，无须为掩盖这类记账增长仓促改机制。

**`ProfileStore.recordedRunIds` 确实按真实结算永久增长。** 每个唯一 RUN_ENDED 追加一个短 ID，防止同一病例重复计奖，localStorage 会跨重载保存；只有 recentRuns≤10，ID 账本无 cap。menu／start／retry 本身不会结算，所以十次菜单重开不能验证十次真实结算的内存。单个未结束的 600 秒压力中这项新增为零。

这项增长是已有契约：`profile.test.ts:193` 检查成功／失败重复确认和重载不重复入账；`:204–210` 明确要求完成 14 局后只显示 10 份记录，但 run-0 仍可被识别为重复且保留最佳。解析还要求 stats.runs 等于 ID 数、best／recent ID 在账本中。直接 cap10／capN 会破坏这些语义和下次载入校验。`formal-failure-lifecycle.spec.ts:53–72` 有一次真实失败、重试、菜单与重载保持记录的语义证据，并非多次结算内存压力。

若未来产品要求长期存档常数大小，需要 schema／API 迁移：由 host 在持久 profile namespace 内发放单调 run serial，用接受区间／水位压缩，并处理旧不透明 ID、跨标签页与乱序结果。任意 opaque UUID 的永久精确成员判定，不能靠任意固定长度的最近数组无损实现。当前安全做法是保留账本并准确说明它的增长；不能为了内存表格好看而取消去重。

## 当前版本最小有效补验

1. 根代理冻结当前 bundle、62 个构建输入、实际 driver 和设备配置，在新的 `completion-v075/performance/attempt-*` 保存独立证据。归档 driver 支持 `VI_PERF_ACTIVE_SECONDS=600`、`VI_PERF_POST_MEMORY=1`；复用前核对冻结路径。正常入口、合法获得 IMMUNE_BEACON／清首守卫／封锁迁移／保留两个开放生产源，准备与 warmup 不计入正式 600 秒。
2. 实测不少于 **600 active 秒**，标准／低各约 300 秒，实际菜单确认设置。每 5 秒 natural 记录 V8 used／capacity／embedder／backing 与 DOM documents／nodes／listeners，保存原始帧间隔、错误及 actor／cell／effects／events／历史／runMetrics 人口。增加只读 label cache 大小采样，以直接覆盖新系统。不要在页面内积累所有全量快照，不在此阶段 forced GC。
3. 正式采样结束后才暂停，验证 tick 不变，等待至少 1.1 秒，分别记自然值与三次 GC 后值；同视图菜单再记一次，再做 5／10 次 start→Q→pause→menu 后同样记录。保持特效／声音／存档／菜单视图一致，允许一次性底图和有界缓存继续存在。
4. 同时列首末 60 秒、逐分钟中位／低位、采样下降、峰值和 matched post-GC 菜单值。capacity 单独上升不是活对象泄漏；低终点也不能代替分析。若相同视图、缓存已热后，0→5 与5→10 两段 collected used／节点／监听器仍同向增长，检查堆保留路径后再归因，无须用额外盲目长跑代替定位。
5. 背景账本和真实结算各加独立针对性说明／观察：合法旅行激活另一器官后记录后台操作与 transactionIds 的增量、回菜单清理；真实结果应只加一个 persisted ID，重复确认／重载加零、recentRuns≤10。**它们不替代 600 秒压力，菜单十重开也不替代真实结算。**

若当前版本这次 600 秒完成、自然曲线没有失控方向、新缓存始终有界、匹配菜单 after-GC 没有逐轮累积 DOM／监听器，就可支持具体的有限结论：在记录的 Windows 开发机、Chrome headless、1366×768、驻心脏双生产源、两档特效下，十分钟 active 压力未观察到持续失控 V8／DOM 保留。实际正增量及上述有意账本应并列报告。总进程／GPU、原生前台与其他路线仍按各自证据范围标记，不把它们变成无限期“无法证明”的泛化阻塞。本预检尚不宣称根代理的新运行通过。
